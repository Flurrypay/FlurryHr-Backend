# FlurryPay HR backend

NestJS, PostgreSQL and Prisma. Run commands from this directory; no root npm package is required.

`npm run build` and `npm run typecheck` regenerate Prisma Client from
`prisma/schema.prisma` before compiling. Missing generated fields such as
`scheduleSnapshot`, `mfaSecretEncrypted` or `mfaVerifiedAt` indicate a stale client
or an outdated schema checkout. Update the backend including its `prisma/`
directory, then run `npm run db:generate` and rebuild. Generation does not modify
the database: apply reviewed migrations with `npm run db:migrate` during the
release procedure before restarting the API. Build with development dependencies
installed, since TypeScript and the Prisma CLI are build tools.

```sh
npm install
npm run setup
npm run dev
```

For later sessions: `npm run db:start`, then `npm run dev`. Local setup writes a private database backup under `.local/backups` before applying migrations. It preserves existing credentials/records. Stop PostgreSQL with `npm run db:stop`. API: http://127.0.0.1:4000/api; health: /api/health. PostgreSQL 16+ binaries and Node.js 22+ are required. `npm run build` compiles and `npm start` runs the production build.

Company and platform accounts are separate. `.env` contains SEED_ADMIN_EMAIL/PASSWORD for the legacy company and PLATFORM_ADMIN_EMAIL/PASSWORD for the dedicated platform operator. The controlled `npm run platform:provision` CLI cannot elevate an existing company identity. Public registration cannot create platform administrators.

Platform operators sign in at `/platform/login`; company owners and employees use
`/login`. There is no shared default platform password. Configure a dedicated
`PLATFORM_ADMIN_EMAIL` and a `PLATFORM_ADMIN_PASSWORD` of at least 16 characters
privately in the backend environment, then run `npm run platform:provision` on the
intended backend/database. Use those credentials and complete authenticator setup.
`npm run db:seed` creates the company owner only. Provisioning refuses to elevate
an existing company account, and rerunning it does not change an existing platform
account's password. Changing the environment password does not reset that account.

Configure ZOHO_EMAIL_API_URL, ZOHO_EMAIL_API_KEY and ZOHO_EMAIL_FROM for real delivery. Preserve MAIL_ENCRYPTION_KEY, generated by setup. Queued bodies remain encrypted until provider acceptance. File transport is test-only.

Tenant models use a request-local fail-closed Prisma client; cross-company relationships are also constrained in SQL. Identity and tenant roles are separate. See docs/ARCHITECTURE.md for boundaries and docs/KNOWN_LIMITATIONS.md for release gates.

Checks: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`, `npm run format:check`. Connected API tests: `npm run test:integration` (alias test:saas). Chrome: `npm run test:browser` (alias test:saas:browser). Tests require the isolated flurryhr_test database, test API/frontend, and file-mail adapter; they check the server's test-environment marker before mutations. `npm run test:homepage` is read-only apart from local demo state. `npm run test:migration` requires a separate empty flurryhr_migration_test database. See root README for environment examples.

## Invitation resend

Resend rotates the token and extends expiry on the same invitation record; it does not create another invitation. The previous link becomes invalid. The invitation list shows the latest invitation for each employee; prior revoked records remain stored. Superseded email attempts remain visible in delivery history.

If the Zoho API is unconfigured, resend fails before changing the invitation. Set ZOHO_EMAIL_API_URL, ZOHO_EMAIL_API_KEY and ZOHO_EMAIL_FROM in backend/.env, then restart the backend.

After revoking an invitation, administrators can delete it with confirmation.
`DELETE /api/invitations/:id` accepts revoked records only and is idempotent.
Deletion uses a `Deleted` status in the existing string field: it removes the
invitation from the list while preserving the employee, audit trail and sending
history. Grouping selects the latest record before excluding deleted entries, so
older revoked records do not reappear. A fresh invitation can be issued afterward.
No schema migration is needed for this change.

## Zoho API delivery

Only Zoho HTTP API delivery is supported for real email. All three variables are required. Set the URL to your ZeptoMail/Zoho CPaaS email-sending endpoint, the key to its Send Mail API key (raw or with the Zoho-enczapikey prefix), and FROM to a verified sender address. Provider acceptance requires the documented EM_104 response. Failed attempts remain retryable. MAIL_TRANSPORT=file is available only for isolated tests; normal delivery uses MAIL_TRANSPORT=zoho.

Reference: https://www.zoho.com/cpaas/help/api/email-sending.html

## Verification and account-security additions

Run test:production-attendance against the isolated test database for attendance, shared CSV and >1,000-employee pagination checks. benchmark:attendance records sequential 10–10,000 employee summary measurements, never production fixtures. db:backup creates a private archive only for the known local development database. test:backup-restore requires isolated migration/restore fixture databases.

Platform users must enroll an authenticator at /platform-security; passwords alone no longer authorize platform APIs. Save the one-time recovery codes privately. MFA verification lasts 30 minutes, and reset requires password plus a second factor. MAIL_ENCRYPTION_KEY protects queued mail and MFA secrets: retain it securely. See docs/MFA_RECOVERY.md.

### Attendance location enforcement

Clock-in and clock-out require a fresh browser location reading (HTTPS in production, location permission enabled). On-site and Hybrid staff use the company attendance point; Remote staff use their individually approved point. HR administrators configure the point, not the employee: use Company Settings (or company onboarding) for the company point, and Add/Edit employee or the invitation form for a remote point. Enter the approved address and exact latitude/longitude; “Use my current location” is appropriate only while physically there. An address is not automatically geocoded.

The server fixes the radius at 100 metres. It rejects unconfigured locations, readings older than two minutes or over ten seconds in the future, and reported accuracy worse than 50 metres. Distance plus reported uncertainty must fit within the 100-metre boundary. Location failure does not create or close attendance; use the existing audited correction workflow for genuine exceptions. There is no administrator attendance bypass. Changes to an approved point take effect on the next attendance action, including clock-out of an open session.

Apply `npm run db:migrate` and rebuild/restart the backend before releasing the matching frontend. Existing approved locations start unset, and old attendance receives no invented GPS proof. Configure each required point before staff mark attendance. The local development database was backed up and migrated on 21 November 2026; production was not changed.

Verification receipts store the location category, radius, distance, reported accuracy and timestamps, not raw device coordinates. The configured remote address/coordinates are personal data; directory/team responses omit another employee’s remote point for non-HR users. Browser coordinates can be deliberately spoofed; this feature checks reported position at attendance actions and is not continuous tracking or proof of physical presence against a hostile device. Tests: `npm test`, `npm run test:saas`, `npm run test:attendance-location-ui`, `npm run test:saas:browser` and the isolated migration test.

Revoking an unaccepted invitation now marks its employee placeholder **Not invited**. Deleting that revoked invitation removes the placeholder from the employee directory and lookup menus, while retaining audit and sending history. A later explicit invitation can reuse the employee record. Migration `202611210003_invitation_employee_status` also repairs placeholders left as Invited by earlier versions; deploy it with `npm run db:migrate` before restarting the updated backend. Existing login accounts are unaffected.
